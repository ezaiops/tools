Reading a JWT

    
A JWT is three base64url segments joined by dots: header.payload.signature. The header says which algorithm signed it (alg) and the token type; the payload carries claims — registered ones like sub (subject), iat (issued at) and exp (expiry) plus whatever your issuer adds. The signature covers the first two segments, which is why decoding alone proves nothing about authenticity — anyone can re-encode a modified payload. Always verify the signature server-side against the issuer's keys.

    
    
      
  • alg: none in the header is a red flag — it asks the verifier to skip signature checking entirely. Never accept it.
    • 
      
  • exp is in seconds since the epoch; expired tokens should be rejected, not silently refreshed.
    • 
      
  • HS256 uses a shared secret; RS256/ES256 use asymmetric keys — signature checks here cover HS256 only.
    • 
    


    
Frequently asked questions

    

      Is it safe to paste a real token here?
      
Decoding happens locally and nothing leaves the page. Still, treat tokens like passwords: if it is a long-lived production token, prefer a throwaway one. The signature check needs your secret, which also never leaves the page.

    

    

      Why does the signature check fail on a valid token?
      
Common causes: the token uses RS256/ES256 (not supported here), the secret has surrounding whitespace, or the token was signed by a different issuer. Only HS256 is checked.

    

    

      Can I edit the payload and re-sign?
      
No — this tool is read-only by design. Tamper-testing belongs in your test suite with your own keys.
